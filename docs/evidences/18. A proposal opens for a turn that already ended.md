# 18. A proposal opens for a turn that already ended

**Pending issue 18 of `PENDING_ISSUES.md`.** The page carries the number
of the issue.

**Verdict: not reproducible. The code has no check, but the order the
issue needs cannot happen with the hooks the daemon installs. No change.**

Evidence collected 2026-09-23, branch `test-battery` at `c4c0666`, watch
1 on `deividfortuna/gha-playground#11`, eight turns of Claude Code
2.1.280. Each turn opened its proposal before it ended.

## The claim

`startTurn` and `endTurn` wait on the same watch lock. If `endTurn` gets
the lock first, it finds no open proposal, and `startTurn` then opens
one for a turn that is over.

## Why the order cannot happen

1. The hook of the agent is synchronous. The daemon installs it with a
   timeout, and `babysitter watch hook` waits for the answer of the
   daemon (`backend/internal/cli/watch.go`: "The agent waits for the
   hook command"). Claude Code runs `UserPromptSubmit` before it reads
   the prompt. The screen of the agent shows it at the start of each
   turn:

   ```
   Meandering…   ( running UserPromptSubmit hooks… 1/2 )
   ```

   `Hook` starts the goroutine of `startTurn` before it answers, so
   that goroutine exists before the agent does any work, and seconds
   before the `Stop` hook exists.
2. That goroutine takes no lock before the watch lock: `startTurn` calls
   `s.locks.lock(id)` first. It waits on the mutex long before `endTurn`
   does.
3. `sync.Mutex` wakes its waiters in the order they came. A woken waiter
   can lose only to a goroutine that arrives at that moment and has not
   slept yet. `endTurn` would have to arrive in the few microseconds of
   the unlock, after a whole turn of the agent.

## What stays true

`proposalBlocker` ignores an open proposal, and `startTurn` does not
check the turn it belongs to. The guard costs little, but no scenario
of the app reaches it, so I changed nothing.

## QA check

**Verdict: not reproduced. I agree with the page above.**

Checked 2026-09-23 at `13f6bfc`. A second daemon watched
`deividfortuna/gha-playground#12` with a fake agent in place of Claude
Code. The fake agent runs the hooks of the `--settings` the daemon
gives it, as Claude Code does, and ends a turn as fast as a process can:
`UserPromptSubmit` as soon as the submit key comes, then `Stop` at once.

```
07:09:05.431Z prompt of 1422 chars
07:09:05.462Z UserPromptSubmit hook took 31ms
07:09:05.487Z Stop hook took 25ms
```

I sent 40 messages with `babysitter watch send`, one after each idle
turn, then 5 more on new watches. After each turn the agent was idle,
and the database held no proposal in `open`:

```
40 agent=idle proposals=[]
$ sqlite3 race.db "select count(*) from proposals"
0
```

Even the fastest turn of an agent is tens of milliseconds long. That is
far more than the gap the issue needs.
